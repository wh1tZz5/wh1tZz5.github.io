用 GitHub Actions 自动化部署静态博客

纯静态博客最大的好处就是部署零成本，而 GitHub Actions 让「写完自动上线」这件事彻底免维护。本文记录一套最小可用的配置：推送即部署，带 lint 校验，失败可回滚。

一、仓库结构

my-blog/
├── .github/
│   └── workflows/
│       └── deploy.yml
├── content/
│   └── posts/
│       └── 2026-01-18-hello.md
├── package.json
└── dist/                # 构建产物，已被 .gitignore 忽略

源文件放在 content/，构建工具（静态生成器或本地脚本）把它们渲染到 dist/。仓库里不提交 dist/，由 CI 现场生成。

二、GitHub Pages 托管方式

GitHub Pages 有两种模式：

  • 从分支：直接发布某个分支（如 gh-pages）的内容。简单，适合纯静态文件。
  • 从 Actions：让 workflow 把 dist/ 上传为 actions/pages 的构建产物。适合有构建步骤的项目。

本文用后者，因为博客内容需要本地先构建。

三、deploy.yml

name: Build & Deploy

on:
  push:
    branches: [ main ]
  workflow_dispatch:    # 允许手动触发

permissions:
  contents: write
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run build        # 输出到 dist/
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v3

关键点

  • npm ci 比 npm install 更可复现，依赖锁定到 package-lock.json。
  • concurrency 防止两个 deploy 作业并行竞争 Pages 部署。
  • id-token: write 是 OIDC 鉴权部署 Pages 必需的。

四、失败回滚

Pages 部署失败时，站点保持上一个成功版本，不会下线。手动排查：

git revert <bad-commit>
git push origin main
# 触发新的 workflow，恢复上一个可构建版本

五、小结

整套配置不到 50 行，覆盖推送即构建、上传产物、部署、并发保护和手动回滚。博客本身是纯静态的，CI 只需做构建这一步，其余完全交给 GitHub Pages 托管。
